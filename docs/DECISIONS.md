## 제품 방향

| 결정 | 이유 |
|---|---|
| **사진을 서버로 보내지 않는다** (백엔드 없음) | 제품의 핵심 신뢰 포인트. 개인정보처리방침도 이 전제로 작성됨. 서버 비용도 0 |
| 웹은 **진단 + 간단 변환만 무료**, 복구·일괄 처리는 **데스크톱** | 웹 = 유입 창구, 데스크톱(MS 스토어 유료) = 수익. 그래서 웹 곳곳에 "여러 장/복구는 데스크톱에서" 안내 |
| 판정은 단정하지 않고 **"~추정"** 표기 | 휴리스틱 판정이라 틀릴 수 있음. 데스크톱과 같은 원칙 |
| 배지는 **정상 / 의심 / 손상 / 안내** 4종 | 데스크톱과 동일 체계. "안내" = 사진이 아닌 파일 |
| 타깃 시나리오: **"아이폰 사진을 PC로 백업했더니 안 열린다"** | 검색 유입이 가장 많은 상황. 랜딩 제목·meta description·FAQ 모두 이 키워드 중심 |

## 기술 선택

| 결정 | 이유 |
|---|---|
| 순수 JS, 빌드 도구/프레임워크 없음 | 정적 파일만 올리면 끝. 유지보수 단순. 대가: HTML 간 공통부분 복붙 |
| 초기엔 pywebview 로컬 상주형(②)으로 시작 → 이후 브라우저형(①)을 별도로 만듦 | ②는 원본 `PLATFORM_EXPANSION.md`에서 채택한 "로컬 상주 + 웹 UI" 방향. ①은 설치 없이 URL로 접속 가능해서 유입에 유리 → 현재 주력 |
| `core/`를 원본 저장소에서 **복사** (단일 소스 아님) | Qt 의존 없는 순수 Python이라 그대로 재사용 가능. 공유 패키지화는 보류 |
| HEIC 디코딩은 **libheif-js (CDN, 1.19.8 고정)** | 브라우저가 HEIC를 기본 지원 안 함. WASM 빌드가 있는 가장 현실적 선택 |
| 라이브포토는 **libheif 없이 바이트 정규식** | 픽셀을 그릴 필요가 없고 UUID만 찾으면 됨. 데스크톱 `core/live_photo_finder.py`와 같은 원리 |
| MOV→MP4는 **외부 라이브러리 없이 직접 remux** | CDN/라이선스(ffmpeg.wasm 등) 걱정 없음, 빠르고 화질 손실 없음 |
| GitHub Pages + Actions 배포 | 무료, `browser/`만 올리면 됨 |
| 분석 도구·쿠키 없음 | 개인정보처리방침 "수집 없음"과 일치시키기 위해 |
